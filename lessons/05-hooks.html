Hooks: Deterministic Guardrails

Everything you've written so far, including CLAUDE.md, plans and goal conditions, is a request. Hooks are the first thing in this course that is a rule: code that runs every time, whatever the model is thinking.

By the end of this lesson you will

  • Decide when something belongs in a hook rather than in CLAUDE.md
  • Know the hook lifecycle events and which ones can block
  • Read and write the settings.json hook schema, including matchers and handler types
  • Use exit codes and JSON output to block, allow, ask or add context
  • Ship five production recipes: a command firewall, file protection, auto-format, a test gate on Stop, and notifications

Advisory vs deterministic

Picture the session from lesson 1, sixty turns in. Your CLAUDE.md says "never edit .env." It said that on turn one too. Since then the context has filled with test logs, file dumps and a long debugging detour, and the instruction is now one sentence among a hundred thousand tokens. Most of the time Claude still follows it. "Most of the time" is fine for a style preference. It is not fine for "don't force-push to main."

That's the distinction this whole lesson rests on:

Instructions (CLAUDE.md, prompts, goals)Hooks
Who decidesThe model, every timeYour code, every time
ReliabilityHigh, not guaranteed; can degrade with contextDeterministic: the script runs on every matching event
Good forConventions, preferences, how to approach workInvariants, safety, mandatory checks, side effects
Cost of being wrongA style nitShould be zero; that's the point
If breaking a rule would make you say "how did this happen?", the rule belongs in a hook.

A good heuristic: write it in CLAUDE.md first. The first time it gets violated in a way that costs you, promote it to a hook. Hooks also cover things that aren't rules at all, just chores you want done every time: format the file after every edit, ping me when you need input, load the latest ticket into context at startup.

The hook lifecycle

A hook is a handler attached to an event in Claude Code's lifecycle. These are the ones you'll use most:

EventFires whenTypical use
SessionStartSession starts, resumes, clears or compactsInject context: current branch, open ticket, recent failures
UserPromptSubmitYou submit a prompt, before Claude sees itAdd context, block prompts containing secrets
PreToolUseBefore any tool call runsBlock dangerous commands, protect files, rewrite inputs
PermissionRequestA permission prompt is about to be shownAuto-approve or deny specific requests
PostToolUseAfter a tool call succeedsFormat, lint, run related tests, log
StopClaude is about to end its turnGate "done" on tests; this is what /goal uses
SubagentStopA sub-agent finishesValidate a sub-agent's output
PreCompactBefore context is compactedSave a transcript or state snapshot
NotificationClaude needs your attentionDesktop or Slack notification
SessionEndSession endsCleanup, usage logging

Anatomy of a hook

Hooks live in settings files: ~/.claude/settings.json (you, everywhere), .claude/settings.json (the project; commit it), or .claude/settings.local.json (you, this project; gitignore it). Plugins, skills and sub-agents can carry hooks too. The shape is always event → matcher group → handlers:

.claude/settings.jsonjson
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/guard.sh",
            "timeout": 30
          }
        ]
      }
    ]
  }
}

Matchers

For tool events, the matcher filters on the tool name:

  • "*", "" or omitted: match everything.
  • Only letters, digits, _, - and |: an exact name or list, such as "Bash" or "Edit|Write".
  • Anything else is treated as a JavaScript regex, such as "mcp__github__.*" for every tool from one MCP server.

Handler types

typeWhat runsUse it for
commandA shell command; event JSON on stdinAlmost everything. Start here.
httpA POST to a URLCentral policy services, audit logging
promptA small model judges the event ($ARGUMENTS holds the input JSON)Fuzzy checks you can't express as a regex. /goal is one of these.
mcp_toolA tool on an MCP serverReuse an existing integration
agentA sub-agent (experimental)Checks that need to read files or run tools

Use $CLAUDE_PROJECT_DIR in commands so they resolve to the project root regardless of where Claude's working directory has wandered. Quote it, because paths can contain spaces. Run /hooks to browse what's configured and where each hook came from. Set "disableAllHooks": true to switch them off without deleting anything.

The contract: stdin, exit codes, JSON

A command hook is a tiny program with a simple contract. It receives a JSON object on stdin describing the event:

{
  "session_id": "abc123",
  "transcript_path": "~/.claude/projects/my-app/abc123.jsonl",
  "cwd": "/Users/me/my-app",
  "permission_mode": "default",
  "hook_event_name": "PreToolUse",
  "tool_name": "Bash",
  "tool_input": { "command": "rm -rf build/", "description": "Clean build output" }
}

It communicates back through its exit code:

Exit codeMeaningEffect
0SuccessContinue. If stdout is a single JSON object, it's parsed for decisions (below).
2Blocking errorstderr is the reason. On events that can block (PreToolUse, UserPromptSubmit, Stop and others) the action is stopped and the reason goes to Claude. PostToolUse can't undo a tool that already ran.
anything elseNon-blocking errorShown as a hook error; the action continues. A crashing hook does not block.
⚠
Fail-open by default

Only exit code 2 blocks. If your guard script has a typo and exits 1, or jq isn't installed and it exits 127, the dangerous command goes through. Test guard hooks against the inputs they're meant to stop. The lab below exists for exactly that.

For finer control, exit 0 and print JSON. The fields you'll use most:

FieldWhereEffect
hookSpecificOutput.permissionDecisionPreToolUse"allow", "deny", "ask" or "defer", with permissionDecisionReason
hookSpecificOutput.additionalContextSeveral eventsAdds a string to Claude's context: a nudge, not a block
decision: "block" + reasone.g. Stop, PostToolUseStop: Claude must keep working, and reason says why. PostToolUse: feedback to Claude.
continue: false + stopReasonAnyHalts Claude entirely
systemMessageAnyA message shown to the user

hookSpecificOutput must include hookEventName:

{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "Production database writes are not allowed"}}

Five production recipes

These are the hooks I'd put in nearly every repo. Each script reads stdin with jq, so install that first. Make the scripts executable (chmod +x .claude/hooks/*.sh) and commit them along with .claude/settings.json so the whole team gets them.

1 · The command firewall (PreToolUse · Bash)

.claude/hooks/block-dangerous.shbash
#!/usr/bin/env bash
# Block destructive or irreversible shell commands before they run.
cmd="$(jq -r '.tool_input.command // empty')"

deny=(
  'rm +-(rf|fr) +(/|~|\$HOME)( |$)'      # rm -rf on root or home
  'git +push.*(--force|-f( |$))'          # force push
  'git +reset +--hard'                    # throws away work
  'curl[^|]*\| *(ba)?sh'                  # pipe-to-shell installs
  '(DROP|TRUNCATE) +(TABLE|DATABASE)'     # destructive SQL
)
for re in "${deny[@]}"; do
  if grep -Eiq -- "$re" <<<"$cmd"; then
    echo "Blocked: '$cmd' matches a dangerous pattern ($re). Ask the user to run it manually if it's really intended." >&2
    exit 2
  fi
done
exit 0

The stderr message is written for Claude, not you. It explains what happened and what to do next, so the agent adapts instead of retrying the same command three times.

2 · Protect secrets and lockfiles (PreToolUse · Edit|Write)

.claude/hooks/protect-files.shbash
#!/usr/bin/env bash
# Deny edits to secrets, lockfiles and git internals, with a structured reason.
path="$(jq -r '.tool_input.file_path // empty')"
case "$path" in
  *.env|*.env.*|*/secrets/*|*package-lock.json|*pnpm-lock.yaml|*yarn.lock|*/.git/*)
    jq -n --arg p "$path" '{
      hookSpecificOutput: {
        hookEventName: "PreToolUse",
        permissionDecision: "deny",
        permissionDecisionReason: ("\($p) is protected. Lockfiles change via the package manager; secrets are edited by humans.")
      }
    }'
    ;;
esac
exit 0
💡
Hooks and permission rules work together

For simple cases, "permissions": {"deny": ["Read(./.env)", "Edit(./.env)"]} in settings.json does the job without a script. Reach for a hook when you need logic: patterns across many paths, exceptions, or a custom message.

3 · Auto-format after every edit (PostToolUse · Edit|Write)

.claude/hooks/format.shbash
#!/usr/bin/env bash
# Format the file Claude just touched. Never fail the turn over formatting.
path="$(jq -r '.tool_input.file_path // empty')"
case "$path" in
  *.ts|*.tsx|*.js|*.jsx|*.json|*.css|*.md)
    npx --no-install prettier --write "$path" >/dev/null 2>&1 || true ;;
  *.py)
    ruff format "$path" >/dev/null 2>&1 || true ;;
  *.go)
    gofmt -w "$path" >/dev/null 2>&1 || true ;;
esac
exit 0

Formatting in a hook means Claude never spends a turn on whitespace, and your diffs stay clean. It also means you can delete "always run prettier" from CLAUDE.md, which frees context for instructions only the model can follow.

4 · The test gate (Stop)

This is the hook version of lesson 4's finish line, and stricter than /goal: the hook runs the tests itself instead of reading the transcript. If they fail, it returns decision: "block" and Claude has to keep working.

.claude/hooks/test-gate.shbash
#!/usr/bin/env bash
# Don't let Claude stop while the test suite is red, but give up after 3 tries
# so a genuinely impossible task can't loop forever.
input="$(cat)"
session="$(jq -r '.session_id' <<<"$input")"
counter="${TMPDIR:-/tmp}/claude-test-gate-$session"

# Only gate turns that changed code; skip if nothing is modified.
if git -C "$CLAUDE_PROJECT_DIR" diff --quiet && git -C "$CLAUDE_PROJECT_DIR" diff --cached --quiet; then
  exit 0
fi

if output="$(cd "$CLAUDE_PROJECT_DIR" && npm test --silent 2>&1)"; then
  rm -f "$counter"; exit 0
fi

tries=$(( $(cat "$counter" 2>/dev/null || echo 0) + 1 ))
echo "$tries" > "$counter"
if [ "$tries" -gt 3 ]; then
  rm -f "$counter"
  jq -n '{systemMessage: "Test gate gave up after 3 attempts; tests are still failing."}'
  exit 0
fi

jq -n --arg out "$(tail -n 30 <<<"$output")" '{
  decision: "block",
  reason: ("Tests are failing. Fix them before finishing. Last output:\n" + $out)
}'
∞
Every Stop gate needs an escape hatch

A Stop hook that blocks unconditionally creates an infinite loop: Claude tries to stop, gets blocked, tries again, forever. The retry counter above is one escape hatch. Claude Code also sets stop_hook_active: true in the Stop hook's input when Claude is already continuing because of an earlier Stop-hook block. Check it with jq -r '.stop_hook_active' to let a second attempt through, and note that Claude Code caps this at 8 consecutive continuations anyway. Keep the test command fast, too. Gate on unit tests, not your 20-minute e2e suite.

5 · Notify me when Claude needs input (Notification)

.claude/hooks/notify.shbash
#!/usr/bin/env bash
# Desktop notification when Claude is waiting on you.
msg="$(jq -r '.message // "Claude needs your attention"')"
if command -v osascript >/dev/null; then
  osascript -e "display notification \"${msg//\"/\\\"}\" with title \"Claude Code\""
elif command -v notify-send >/dev/null; then
  notify-send "Claude Code" "$msg"
fi
exit 0

Hooks are code you run with your permissions

🔒
Review hooks like you review code, because they are code

Command hooks run automatically, as you, with your full user permissions, on every matching event. A hook in a project's .claude/settings.json runs when you open that project with Claude Code. Before trusting a repo you've cloned, read its .claude/ directory. Use /hooks to see exactly what's active and where it came from.

Practical hygiene:

  • Quote every variable and use jq rather than string-splitting JSON. Tool inputs are model-generated text; treat them as untrusted input to your script.
  • Keep hooks fast. A PreToolUse hook runs before every matching tool call; 500 ms on every Bash adds up.
  • Fail safe where it matters. For a security guard, consider exiting 2 when the script can't parse its input, rather than failing open.
  • Hooks aren't a sandbox. Pattern-matching shell commands is a strong speed bump, not a security boundary. Determined obfuscation can get past regexes. For real isolation, use Claude Code's sandboxing or a container.

Try it: hooks in a live session

A scripted session with all five recipes installed. Ask Claude to do something dangerous, touch a secret, or ship a feature, and watch the hooks fire.

Key takeaways

  • Instructions are advisory; hooks are deterministic. Promote a rule to a hook the first time breaking it costs you.
  • Guardrails live on PreToolUse (block before) and Stop (gate "done"). Chores live on PostToolUse, SessionStart and Notification.
  • The contract: JSON on stdin; exit 2 blocks with stderr as the reason; exit 0 plus JSON gives fine-grained decisions. Other exit codes fail open.
  • Every Stop gate needs an escape hatch so it can't loop forever.
  • Hooks run as you. Read .claude/ before trusting a repo, and check /hooks.
