Context Is the Program

Every session starts from zero, except for the few hundred lines you choose to load first. CLAUDE.md is the most leveraged file in your repo. Most teams treat it like a junk drawer.

By the end of this lesson you will

  • Know every place Claude Code looks for memory files, and the order they load in
  • Write a CLAUDE.md that is short, specific and checkable, and know what to leave out
  • Use @imports, .claude/rules/ and CLAUDE.local.md to keep memory modular

The program you didn't know you were writing

In lesson 1 we wrote the agent loop in twelve lines, and the first line was context = [system_prompt, project_memory, task]. The model has no persistent memory of your codebase. It doesn't remember yesterday's session or that your team switched to pnpm last spring. Each session it knows exactly what is in that list, and nothing else.

That makes the context window the closest thing an agent has to a program. Your prompt is a function call. CLAUDE.md is the standard library that gets imported into every call. When people say Claude "ignores conventions," the convention is usually missing from context, or buried in a sea of other text.

If an instruction isn't in the context window, it doesn't exist. If it's in there with 300 other instructions, it barely exists.

This lesson is about curating that window: what goes in permanently (memory files), what goes in on demand (imports, rules, skills), and how to keep a long session from drowning in its own logs.

Where memory files live

Claude Code reads memory from several places and concatenates them. Nothing overrides anything; it all lands in context together. Broader scopes load first, more specific ones after.

Already have an AGENTS.md?

If a repo has AGENTS.md and no CLAUDE.md, Claude Code reads AGENTS.md instead. If you want both, a one-line CLAUDE.md containing @AGENTS.md keeps them in sync.

What belongs in CLAUDE.md

A good test for each line: would a sharp new teammate get this wrong on their first day without being told? If yes, it belongs. If they'd figure it out from the code in 30 seconds, it's noise. Here's what consistently earns its place:

  1. Commands. How to build, test a single file, lint, typecheck, run migrations. This is the highest-value section by far, because it's what lets the agent verify its work.
  2. A map. Three to six bullets on where things live and how a request flows. It saves dozens of exploratory reads per session.
  3. Non-obvious conventions. "Money is integer cents." "Never edit an applied migration." Not "write clean code."
  4. Workflow expectations. "Propose a plan for multi-file changes." "Run typecheck and tests before reporting done."
  5. Known gotchas. The flaky test, the env var that must be set, the generated file you shouldn't edit by hand.

And here is what doesn't belong, even though it often ends up there:

  • Pasted documentation. API references and wiki pages bloat every session. Link them with an import or let Claude read them when needed.
  • Vague virtues. "Follow best practices" costs tokens and changes nothing. The model already wants to write good code; tell it what good means here.
  • Secrets. The file is in git and loaded into every session. Point to where secrets live instead.
  • Anything that must never happen. CLAUDE.md is advisory. If a rule breaking would be a real incident, enforce it with a hook or a permission rule (lesson 5).
💡
Keep it under ~200 lines

The official guidance is to keep each CLAUDE.md under roughly 200 lines. Every line costs context in every session, and long files dilute attention: the one rule that matters competes with forty that don't. Start with /init, then delete more than you add.

A reference CLAUDE.md

This is a realistic shape for a mid-sized web app. It runs about 25 lines and every line is either a command, a fact about the code, or a checkable rule.

CLAUDE.md~25 lines
# shop-web

Next.js 15 storefront + tRPC API. Postgres via Prisma. pnpm workspace.

## Commands
- `pnpm dev` — start app on :3000
- `pnpm test path/to/file` — run one test file (Vitest)
- `pnpm typecheck && pnpm lint` — run both before saying a task is done
- `pnpm db:migrate` — apply migrations (never edit an applied migration)

## Architecture
- `app/` routes → `server/routers/*` (tRPC) → `server/services/*` → Prisma
- Business logic lives in services, never in route handlers
- API reference: @docs/api.md

## Conventions
- TypeScript strict; no `any` without a `// reason:` comment
- Money is integer cents (`priceCents`), never floats
- Every bug fix gets a regression test next to the code (`*.test.ts`)

## Workflow
- Multi-file change? Propose a plan first.
- YOU MUST run `pnpm typecheck && pnpm test` and show the output before reporting done.

Notice the single shouted rule at the end. Emphasis works because it's rare. If everything is IMPORTANT, nothing is.

Keep memory modular: imports, rules, local files

As a project grows, one CLAUDE.md becomes either too long or too vague. Claude Code gives you three tools to split it without losing anything.

@imports: link, don't paste

Anywhere in a memory file, @path/to/file pulls that file in. Relative paths resolve from the importing file, and imports can nest up to four hops deep. Use it to reference docs that already exist instead of copying them.

# CLAUDE.md
See @README.md for the project overview and @package.json for scripts.

## Deeper references
- Git workflow: @docs/git-workflow.md
- My personal overrides: @~/.claude/my-shop-notes.md

.claude/rules/: one topic per file

Markdown files in .claude/rules/ (searched recursively) are loaded as memory too. Each team or concern can own a small file, such as testing.md, api-design.md or security.md, instead of everyone fighting over one document. Rules can be path-scoped with frontmatter, so frontend rules only load when Claude touches frontend files:

.claude/rules/react.mdpath-scoped
---
paths:
  - "app/**/*.tsx"
  - "components/**/*.tsx"
---
# React conventions
- Server components by default; add "use client" only for interactivity
- Co-locate component tests as `Component.test.tsx`
- Use the `cn()` helper from `lib/utils` for conditional classes

CLAUDE.local.md: yours, not the team's

Your staging URL, your seeded test account, your preference for verbose test output: put these in CLAUDE.local.md at the project root and add it to .gitignore. It loads after the project file, so it's read last.

Auto memory and /memory

Separately from the files you write, Claude Code keeps an auto memory: a MEMORY.md index plus topic files under ~/.claude/projects/<project>/memory/. Claude saves things it learns about you and the project, such as a correction you gave or a build quirk it discovered, and the start of MEMORY.md loads into future sessions. It's on by default. You can turn it off with "autoMemoryEnabled": false in settings.

Two commands manage all of this:

  • /init scans the repo and drafts a CLAUDE.md. If one already exists, it suggests improvements instead of overwriting.
  • /memory lists every memory file currently loaded, opens any of them in your editor, and toggles auto memory.
🎼
Treat corrections as memory edits

When you catch yourself correcting the same thing twice ("no, we use pnpm"), stop and fix the source. Ask Claude to add the rule to CLAUDE.md, or open it with /memory. Every correction you don't persist, you'll make again next week.

Advisory, not enforcement

It's worth being blunt about the limits. CLAUDE.md is context: Claude reads it and usually follows it, but nothing guarantees it. On turn 80 of a long session, with 60,000 tokens of logs between the rule and the decision, "never push to main" is a fading memory.

Context rot, and how to stay clean

Memory is what you load at the start. Hygiene is what you do as the session goes on. Every file read and test log stays in the window, and as it fills, older instructions get less attention. Eventually Claude Code compacts the history automatically, and details can fall out in the summary. Four habits keep you ahead of it:

  1. /clear between tasks. Finished the bug fix and starting a feature? Clear. Memory files reload; yesterday's stack traces don't.
  2. /compact with a focus. When you need to keep going but the window is heavy, compact on your terms, for example /compact keep the API contract decisions and the list of failing tests. You choose what survives instead of leaving it to chance.
  3. State lives in files. For anything multi-step, have Claude maintain PLAN.md or progress.md with a checklist. Files survive /clear, compaction and new sessions, and they're reviewable in git.
  4. Check /context when quality dips. A session that suddenly feels "dumber" is usually just full.
progress.mdpattern
# Migrate checkout to Stripe Payment Element
Started: 2026-10-18 · Branch: feat/payment-element

## Done
- [x] Characterization tests for current checkout (tests/checkout.spec.ts)
- [x] Server: create PaymentIntent endpoint

## Next
- [ ] Client: replace CardElement with PaymentElement
- [ ] Remove legacy /api/charge route

## Decisions
- Keep idempotency keys in Redis (not Postgres): see thread in PR #412

Ask Claude to update the file at the end of each step. Then a fresh session only needs one instruction: "Read progress.md and continue."

Key takeaways

  • The context window is the agent's whole world. CLAUDE.md is the part of it you control for every session, so treat it like code.
  • Memory files concatenate, from managed and user scope down to project, local and subdirectory. Nothing overrides; conflicts just create ambiguity.
  • Put in commands, a map, non-obvious conventions and gotchas. Leave out pasted docs, vague virtues and secrets. Stay under ~200 lines.
  • Split with @imports, .claude/rules/ and CLAUDE.local.md, rather than growing one giant file.
  • CLAUDE.md is advisory. Hard rules belong in permissions and hooks.
  • Manage the window as you go: /clear between tasks, /compact with a focus, state in files.
