Skills: Teach It Once

Every team has rituals the agent keeps getting slightly wrong: the release checklist, the API error format, the way migrations must be written. Skills turn that tribal knowledge into folders Claude loads exactly when it needs them — and ignores the rest of the time.

20 min read1 lab1 simulatorQuiz

By the end of this lesson you will

  • Explain progressive disclosure and why it lets you install dozens of skills without bloating context
  • Write a SKILL.md with frontmatter that actually triggers when it should — and stays quiet when it shouldn't
  • Choose between a skill, CLAUDE.md, a hook and a sub-agent for any piece of know-how
  • Ship three production-ready skills: a scripted one, a user-only command, and a reference skill

The problem skills solve

In lesson 2 you learned that CLAUDE.md is loaded into every session. That's its superpower and its curse. It's the right home for "we use pnpm" and "tests live next to the code." It's the wrong home for the 80-line procedure for cutting a release, which matters twice a month and costs context on every single turn in between.

So people do one of two things. They stuff CLAUDE.md until it becomes a 900-line wall the model skims. Or they keep the procedure in their head and re-type it — slightly differently each time — whenever it's needed. Both fail the same way: the agent either drowns in irrelevant instructions or never gets the relevant ones.

A skill is know-how with a trigger condition. It costs a sentence of context until the moment it's needed — then it costs whatever it needs to.

Concretely, a skill is a folder containing a SKILL.md file: YAML frontmatter that says what it is and when to use it, followed by a markdown playbook. The folder can also carry supporting files — reference docs, templates, scripts — that the playbook points to.

Progressive disclosure: three levels of loading

The design idea that makes skills work is borrowed from good UI: show the minimum up front, reveal detail on demand. Claude Code loads a skill in three stages.

  1. Metadata — always loaded. The name and description of every available skill sit in context so Claude knows what exists. This is why the description is the most important line you'll write.
  2. Body — loaded when used. When Claude decides a skill fits the task (or you invoke it with /name), the full SKILL.md body enters context.
  3. Supporting files — loaded when referenced. If the body says "see reference/errors.md for the error catalogue," that file is read only if the task needs it. Scripts in the folder are executed, not read — so a 300-line parser costs you only its output.
◆
Scripts are the secret weapon

Deterministic work — parsing git logs, validating a schema, filling a PDF — is cheaper, faster and more reliable as code than as instructions. Put it in scripts/, tell the skill when to run it, and let the model do the judgment parts.

Anatomy of a skill

Skills live in a folder named after the skill. Where that folder lives decides who gets it:

ScopePathUse for
Project.claude/skills/<name>/SKILL.mdTeam know-how — commit it, everyone gets it
Personal~/.claude/skills/<name>/SKILL.mdYour own habits, across every repo
Plugin<plugin>/skills/<name>/SKILL.mdShared across teams; invoked as /plugin-name:skill-name
Enterprisemanaged settings directoryOrg-wide policy and playbooks

When names collide, enterprise beats personal, and personal beats project. A skill also wins over a legacy command file with the same name.

release-notes/
├── SKILL.md              # required: frontmatter + playbook
├── templates/
│   └── notes.md          # read when the body references it
└── scripts/
    └── commits.sh        # executed; only its output enters context

Frontmatter fields

Every field is technically optional — name defaults to the folder name — but in practice you always want a sharp description. Field names must match exactly; unknown fields are silently ignored, so a typo like allowed_tools fails without a warning.

FieldWhat it does
nameThe skill's identity and its slash command (/name). Defaults to the directory name.
descriptionWhat it does. Always in context; Claude uses it to decide when to load the skill.
when_to_useExtra trigger text appended to the description. Keeps "what" and "when" readable.
argument-hintAutocomplete hint shown in the / menu, e.g. [issue-number].
disable-model-invocationtrue = only you can run it by typing /name. Use for anything with side effects.
user-invocablefalse hides it from the / menu — background knowledge only Claude pulls in.
allowed-toolsTools pre-approved while the skill runs, so a trusted workflow doesn't stop for permission prompts.
context: forkRuns the skill in a sub-agent with its own context window; only the result comes back.
modelPer-turn model override — e.g. a cheaper model for a mechanical skill.

Arguments and paths

When you invoke a skill with arguments — /fix-issue 1234 — the body can reference them. $ARGUMENTS expands to everything you typed after the name; $0 (or $ARGUMENTS[0]) picks one by index. ${CLAUDE_SKILL_DIR} expands to the skill's own folder, which is how a body reliably points at its bundled scripts no matter where the session's working directory is.

Skills vs. slash commands

If you've used Claude Code for a while, you may have .claude/commands/deploy.md files. They still work, and they create /deploy just like .claude/skills/deploy/SKILL.md does. The difference is that a skill is a folder — it can carry scripts and references — and it can be picked up automatically by Claude, not only typed by you. For anything new, write a skill. A "command" is now simply a skill you choose to invoke by hand.

Writing descriptions that actually trigger

Here's the uncomfortable truth: most skills that "don't work" are fine skills with bad descriptions. Claude never sees the beautiful playbook because nothing in the one-line description connected it to what the user asked.

A description has one job — to be matched against a request the skill author will never see. That means writing it in the vocabulary of the request, not the vocabulary of the solution. Three ingredients:

  • What it does, with concrete verbs: generate, validate, fill, migrate.
  • When to use it: "Use when the user asks for…, mentions…, or is about to…".
  • Keywords people actually type: file types, tool names, domain nouns. "PDF", "AcroForm", "changelog", "tag", "migration", "column".
Weak descriptionStrong description
Helps with releases.Generate release notes and a changelog entry from git commits between two tags. Use when the user asks what changed since a version, or is preparing a release.
Database utility.How to write safe Prisma migrations: additive changes, backfills, zero-downtime column renames. Use when changing the schema or adding a column or table.
Our API standards.REST conventions for this repo — route naming, error envelope, pagination, zod validation. Use when creating, changing or reviewing an HTTP endpoint.

The flip side matters too: a description that's too broad ("Use for any coding task") will load on everything and dilute the context it was meant to protect. Specific beats clever.

Skill, CLAUDE.md, hook or sub-agent?

By now you have four places to put "how we do things here." They aren't interchangeable, and choosing wrong is the most common harness mistake. The test is two questions: how often is this relevant, and does it need to be guaranteed?

Put it in…When the know-how is…Example
CLAUDE.mdRelevant to almost every task; short"Use pnpm. Run pnpm test before committing."
SkillRelevant sometimes; a procedure or reference; may bundle scriptsThe release checklist; the API error catalogue
HookMust happen (or never happen) every time, no exceptionsBlock edits to .env; run prettier after every edit
Sub-agentA role needing its own context, tools or modelA read-only reviewer; a test runner that swallows noisy logs
⚠
Skills are advice, not enforcement

A skill's playbook is followed by the model, so it's subject to the same drift as any instruction. If a step is non-negotiable — "never deploy without tests passing" — back the skill with a hook (lesson 5) rather than writing it in capital letters.

Three skills worth stealing

Each of these demonstrates a different shape. Copy them, then edit until they describe your repo rather than mine.

1. A scripted skill: release notes

The judgment (what's user-facing, how to phrase it) belongs to the model; the mechanics (which commits, which PRs) belong to a script.

.claude/skills/release-notes/SKILL.mdmarkdown
---
name: release-notes
description: Generate release notes and a CHANGELOG.md entry from git commits between two tags. Groups changes into features, fixes and breaking changes.
when_to_use: Use when the user asks for release notes, a changelog, what changed since a version, or is preparing a release or tag.
argument-hint: [from-tag] [to-ref]
allowed-tools: Bash(git log *), Bash(git describe *), Read, Edit
---

# Release notes

1. Collect commits:
   `bash ${CLAUDE_SKILL_DIR}/scripts/commits.sh $0 $1`
   (defaults: last tag → HEAD). The script prints one line per commit:
   `type|scope|subject|pr-number`.
2. Drop chore/ci/test commits unless they change user-visible behavior.
3. Group into **Breaking**, **Features**, **Fixes**. Breaking first, always.
4. Rewrite each subject for users, not developers: say what changed for them.
5. Fill `${CLAUDE_SKILL_DIR}/templates/notes.md` and prepend it to CHANGELOG.md.
6. Show me the entry before committing anything.

## Gotchas
- A commit with `!` after the type (e.g. `feat!:`) is breaking even without a footer.
- Squash-merged PRs: use the PR title, not the individual commits.
.claude/skills/release-notes/scripts/commits.shbash
#!/usr/bin/env bash
# Print conventional commits between two refs as: type|scope|subject|pr
set -euo pipefail
FROM="${1:-$(git describe --tags --abbrev=0)}"
TO="${2:-HEAD}"
git log "$FROM..$TO" --no-merges --pretty=format:'%s' |
  sed -E 's/^([a-z]+)(\(([^)]*)\))?(!)?: (.*)$/\1\4|\3|\5/' |
  sed -E 's/^(.*)\(#([0-9]+)\)$/\1|\2/'

2. A user-only command: fix an issue

This one has side effects — it creates branches and opens PRs — so disable-model-invocation: true means Claude can never decide to run it on its own. You type /fix-issue 1234; it does the rest.

.claude/skills/fix-issue/SKILL.mdmarkdown
---
name: fix-issue
description: Fix a GitHub issue end to end — reproduce, test, fix, open a PR.
argument-hint: [issue-number]
disable-model-invocation: true
---

Fix GitHub issue #$ARGUMENTS.

1. `gh issue view $ARGUMENTS` — read the issue and every comment.
2. Find the relevant code. Summarize the root cause in 2–3 sentences before editing.
3. Write a failing test that reproduces the bug. Run it; confirm it fails.
4. Make the smallest fix that turns it green. Run the full suite and the type check.
5. Create branch `fix/$ARGUMENTS-<short-slug>`, commit with `fix: … (closes #$ARGUMENTS)`.
6. `gh pr create` with: root cause, the fix, how it was verified.

If you cannot reproduce the bug, stop and tell me what you tried. Do not guess-fix.

3. A reference skill: API conventions

No steps at all — just knowledge, loaded only when someone touches an endpoint. The heavy catalogue lives in a separate file so even the body stays small.

.claude/skills/api-conventions/SKILL.mdmarkdown
---
name: api-conventions
description: REST API conventions for this repo — route naming, error envelope, pagination, zod validation and status codes.
when_to_use: Use when creating, changing or reviewing an HTTP endpoint, route, controller or API response.
user-invocable: false
---

# API conventions

- Routes: plural nouns, kebab-case: `/api/v1/order-items/:id`. No verbs in paths.
- Validate every body and query with zod in `src/schemas/`; never trust `req.body` directly.
- Errors always use the envelope:
  `{ "error": { "code": "ORDER_NOT_FOUND", "message": "…", "details": {} } }`
- Pagination: cursor-based. `?cursor=<opaque>&limit=50` (max 200).
  Response includes `nextCursor` (null on the last page).
- Status codes: 201 create, 204 delete, 409 conflict, 422 validation. Never 200 for errors.

Full error-code catalogue: see `reference/error-codes.md` (read it only when adding a new code).

Sharing skills: plugins

Checking .claude/skills/ into the repo shares skills with everyone who works on that repo. To share across repos and teams, package skills — together with agents, hooks and MCP servers — as a plugin. Run /plugin to browse and install from marketplaces, or install from the shell:

# install a plugin from a marketplace
claude plugin install code-review@claude-plugins-official

Plugin skills are namespaced — /plugin-name:skill-name — so two plugins can both ship a review skill without colliding.

💡
Grow skills from real sessions

The best skills aren't designed up front. When you notice you've explained the same procedure to Claude for the third time, ask it: "Turn what we just did into a skill in .claude/skills/." Then edit the result. The session is the first draft.

Key takeaways

  • A skill is know-how with a trigger: a folder with a SKILL.md, optionally carrying references and scripts.
  • Progressive disclosure keeps it cheap — only name and description load until the skill is used; files load when referenced; scripts run and return output.
  • The description is the whole ballgame. Write what + when + the keywords users actually type.
  • Use disable-model-invocation: true for anything with side effects; user-invocable: false for background knowledge.
  • Pick the right home: CLAUDE.md for always, skills for sometimes, hooks for must, sub-agents for separate roles.
