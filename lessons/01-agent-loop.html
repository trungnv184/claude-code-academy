The Agent Loop

Coding agents feel like magic until they confidently ship the wrong fix. Both behaviors come from the same twelve-line loop, and once you see it you'll know exactly where to intervene.

By the end of this lesson you will

  • Describe an agent as model + tools + loop, and explain why the loop is the part you control
  • Recognize the three phases — gather, act, verify — in any agent transcript
  • Name the five classic agent failure modes and which harness layer fixes each
  • Run your first Claude Code session (simulated) and know the handful of commands you'll use daily

From autocomplete to delegation

Most of us met AI coding through autocomplete: you type, it guesses the next line, you hit Tab. Then came chat: you paste code into a window, it pastes code back, and you are the one who runs it, reads the error and pastes again. In both modes, you are the loop. The model is a very fast, very well-read intern who has never been allowed to touch the keyboard.

Claude Code changes one thing, and that one thing changes everything: it gets the keyboard. It can read files, search, edit, run your test suite, look at the failure and try again. It runs in your terminal, in your repo, with your tools. You stop being the loop and start being the person who designs the loop.

The skill is no longer "write the code." It's "set up the conditions under which correct code is the most likely outcome."

That's what this course is about. Not prompts — the harness: the context, plans, finish lines, guardrails, reusable know-how and team of helpers that surround the model. Get the harness right and a mediocre prompt still lands. Get it wrong and a brilliant prompt still drifts.

What an agent actually is

Strip away the branding and every coding agent is the same shape. Here it is in pseudocode — this is genuinely most of it:

agent.py (conceptual)~12 lines
def agent(task, tools):
    context = [system_prompt, project_memory, task]
    while True:
        reply = model(context)                 # think + decide
        if reply.wants_tool:
            result = tools[reply.tool](reply.args)   # act on the world
            context.append(reply)
            context.append(result)             # observe the outcome
        else:
            return reply.text                  # model decided it's done

Three things to notice, because every lesson that follows is a way of pulling one of these levers:

  1. The context is everything the model knows. It starts with a system prompt and your project memory (CLAUDE.md), and grows with every tool result. Nothing outside it exists. → Lesson 2
  2. The model decides when it's done. That else: return branch is the single most dangerous line. If "done" is a feeling rather than a fact, you get premature victory. → Lesson 4
  3. Tools are where intent meets the world. Every tools[...]() call is a point where you can inspect, block or augment what happens — deterministically, outside the model. → Lesson 5

Gather → Act → Verify

Watch any good agent transcript and you'll see the loop break into three recurring phases. Anthropic describes Claude Code's own loop this way, and it's the most useful lens for reading — and steering — what the agent does.

Gather: the phase people under-invest in

An agent that edits before it understands is guessing. The cheapest improvement you can make to almost any session is to tell it to read first: "look at how auth works in src/auth before proposing anything." Plan mode (lesson 3) formalizes this — it physically prevents edits until you approve a plan.

Act: small, reversible steps

Agents are best at small diffs they can immediately check. A 40-line change followed by a test run beats a 400-line change followed by hope. Claude Code checkpoints edits so you can rewind (Esc Esc), but your real safety net is git: commit at green.

Verify: the phase that makes the rest trustworthy

Verification is what turns an agent from a confident guesser into an engineer. Tests, type checks, linters, a screenshot of the rendered UI, a second agent reviewing the diff — anything that returns a fact the model can't talk its way around. Boris Cherny, who created Claude Code, has said that giving Claude a way to verify its own work is probably the single most important thing for getting great results. Every advanced technique in this course is, at heart, a way to make verification automatic.

The context window is a budget

Notice the meter in the lab. Every file read, every test log, every tool result lands in the context window and stays there. It's large — but it isn't free, and it isn't uniform. As the window fills, older details get less attention, sessions get slower and more expensive, and eventually Claude Code compacts (summarizes) the history to make room. Details can fall out in that summary.

Practitioners call the gradual degradation context rot, and managing it is a core skill:

  • /clear between unrelated tasks. A fresh window beats a polluted one. Your CLAUDE.md reloads automatically.
  • Delegate noisy work to sub-agents. A sub-agent can read 40 files and hand back a 10-line summary; only the summary enters your main context. (Lesson 7)
  • Write state to files, not to chat. A PLAN.md or progress.md survives /clear, compaction and even a new session.

Run /context

Five ways agents fail (and the fix for each)

After enough sessions, you stop seeing random failures and start seeing the same five. Each maps neatly onto one layer of the harness:

Failure modeWhat it looks likeHarness fix
AmnesiaUses npm in your pnpm repo. Again. Ignores the conventions you explained yesterday.CLAUDE.md
Wrong approachBuilds a beautiful solution to a slightly different problem. You find out 400 lines later.Plan mode
Premature victory"All tests pass!" (they were never run). "Done!" (half the checklist remains).Goals & loops
Rule driftWas told never to touch .env or run git push --force. Did it anyway, on turn 60.Hooks
Context overloadHuge task, one session; quality degrades as the window fills with logs and file dumps.Skills + Sub-agents

Where you fit: from pair to conductor

Addy Osmani describes a progression in how engineers work with coding agents — from the conductor, guiding a single agent in real time, to the orchestrator, setting up several agents to work in parallel and reviewing their output asynchronously. It's a useful ladder for thinking about your own practice:

StageYou doAgent doesYou need
PairApprove each edit, steer constantlySmall, supervised changesLessons 1–3
ConductorSet the goal and the checks; review the resultA full task, self-verifiedLessons 4–6
OrchestratorDecompose work, run agents in parallel, mergeSeveral tasks at once, in isolationLesson 7–8

Don't skip rungs. Orchestrating five agents without reliable verification just produces five times the plausible-looking wrong code — faster.

Key takeaways

  • An agent is model + tools + loop. You can't change the model's weights, but you control nearly everything about the loop.
  • Read every transcript as gather → act → verify. Most bad outcomes are a starved gather phase or a missing verify phase.
  • Context is a budget. Clear between tasks, push noisy work into sub-agents, persist state in files.
  • The five failure modes — amnesia, wrong approach, premature victory, rule drift, context overload — each have a specific harness fix. The next six lessons cover them one by one.
