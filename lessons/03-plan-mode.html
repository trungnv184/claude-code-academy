Lesson 3 · Plan mode

Plan Before You Code

The most expensive agent mistake isn't a bug. It's a well-tested solution to the wrong problem. Plan mode makes you and the agent agree on the approach while changing it still costs nothing.

20 min read1 lab1 simulatorQuiz

By the end of this lesson you will

  • Run the explore → plan → code → commit workflow and know what each step protects you from
  • Enter plan mode four ways, and know exactly what it blocks and what it allows
  • Review and edit a plan before approving it, and pick the right approval option
  • Know when planning is overhead, and write plan prompts and specs that survive across sessions

The 400-line wrong turn

You ask for Google sign-in. Claude installs Passport, writes a session layer, adds routes and a migration, and starts running tests. Then it discovers the app already uses NextAuth. It isn't stupid; it simply started acting before it finished gathering. By the time anyone notices, there's a 600-line diff, two-thirds of which is getting thrown away.

Agents are biased toward action. A model that sees a task and a set of edit tools will reach for the edit tools, because that looks like progress. In lesson 1's terms, the gather phase gets starved. Plan mode fixes this structurally: while it's on, Claude can read, search and think, but it cannot change your source files until you approve a plan.

A plan is the cheapest code review you will ever do. It's twenty lines long and nothing has been built yet.

Explore → Plan → Code → Commit

The workflow Anthropic recommends for anything non-trivial has four beats. Each one exists to catch a specific failure before it gets expensive.

  • Explore catches wrong assumptions: the existing auth library, the helper that already does this, the test setup.
  • Plan catches wrong approach: the architecture choice, the order of steps, the risky bits nobody mentioned.
  • Code in small, verified steps catches wrong implementation while each diff is still small.
  • Commit at green gives you a rollback point and a reviewable history. Git is your real undo button.

Using plan mode

Four ways in

HowWhen to use it
Shift+Tab (repeat until the status bar reads plan mode on)Mid-session, before a bigger change
/plan or /plan add Google sign-inEnter plan mode and give the task in one go
claude --permission-mode planStart a whole session read-only, e.g. to explore an unfamiliar repo
"defaultMode": "plan" in .claude/settings.jsonMake planning the default for a repo where mistakes are costly

Shift+Tab cycles through the permission modes in order: default (ask before edits) → acceptEdits (auto-approve file edits) → plan → auto → back to default. If you've enabled bypassPermissions it appears in the cycle too, which is one more reason to leave it disabled on your daily machine.

{
  "permissions": {
    "defaultMode": "plan"
  }
}

What it blocks, what it allows

In plan mode Claude can still read files, search, run read-only exploration, delegate research to the built-in Plan sub-agent, and ask you questions. What it can't do is modify your source. When it's ready, it presents a plan and waits for you.

Reviewing and approving

The plan isn't a formality. Read it like a design doc from a fast but new colleague. Press Ctrl+G to open the plan in your editor and change it directly: delete a step, reorder, add a constraint. When you're happy, you choose how execution proceeds:

  • Approve and run in auto mode, when the plan is solid and the change is low-risk.
  • Approve with manual edit approval, when you want to watch each change land.
  • Keep planning, and tell Claude what's wrong. This costs nothing at this stage.
💡
What to look for in a plan

The files it will touch (surprises here are red flags). Whether it reuses existing helpers or invents new ones. Where tests come in: before or after the change? And what it says about risk: migrations, public APIs, data. If the plan doesn't mention verification, ask for it.

When to skip the plan

Planning has a cost: a few extra turns and a few minutes of your attention. The lab's typo scenario makes the point. A useful rule of thumb from Anthropic's own guidance: if you could describe the diff in one sentence, skip the plan.

Skip planningAlways plan
Typo, rename, one-line fixTouches 3+ files or crosses module boundaries
Adding a log line or a test for existing behaviorYou're unsure how the current code works
The exact change is already in your headMigrations, auth, payments, public APIs
Throwaway prototype on a branchAnything you'll hand off to an unattended loop (lesson 4)

Writing a plan prompt that works

A weak planning prompt ("plan the Google login") gets a generic plan. A strong one constrains the search space and tells Claude what you'll be judging:

prompttemplate
Goal: let users sign in with Google.

Context:
- Read src/auth.ts and the accounts model before proposing anything.
- We already use NextAuth; don't introduce a second auth library.

Constraints:
- No new DB columns if the accounts table can hold it.
- Existing email/password users must be able to link Google later.

Plan output:
- Numbered steps, each small enough to verify on its own
- Files touched per step
- Tests to add (and whether they come before the change)
- Risks and open questions you want me to answer

The last block does the most work. You're specifying the shape of the plan, which makes it easier to review and harder for important parts like tests and risks to go missing.

Give it room to think

Planning is where extra reasoning pays off most. /effort sets how much effort the model spends per turn. Raise it for hard design questions, and drop it back down for mechanical work. Extended thinking can be toggled with Option+T (Alt+T). Or simply ask: "think through at least two approaches and compare them before choosing." Asking for alternatives is the cheapest way to avoid anchoring on the first idea.

Plans that outlive the session

A plan that only exists in the chat dies with /clear. For anything bigger than a single session, have Claude write it to a file and keep it updated:

# after approving the plan
> Save this plan to specs/google-signin.md as a checklist.
> As you finish each step, tick it off and note any decision you made.

Now the plan is reviewable in the PR, survives compaction, and any fresh session, or sub-agent, can pick up with "read specs/google-signin.md and do the next unchecked step." This is the foundation lesson 4's loops are built on.

The interview technique

For bigger features, flip the direction: have Claude interview you before it plans. It surfaces the questions you didn't think to answer, such as edge cases, permissions and migration strategy, and turns your answers into a spec.

I want to add team workspaces. Before planning anything, interview me.
Ask one question at a time about requirements, edge cases, permissions
and data migration. When you have enough, write a spec to
specs/workspaces.md. Then start a fresh session to plan from that spec.
🎼
Spec, then fresh session

Interviewing and planning fill the window with back-and-forth. Once the spec is on disk, /clear and plan from the file. The planning session starts from a clean, dense description instead of a long chat transcript.

Key takeaways

  • Agents lean toward action. Plan mode forces the gather phase: read and think, no source edits until you approve.
  • Use explore → plan → code → commit. Your review gate between plan and code is the highest-leverage minute in the loop.
  • Get in with Shift+Tab, /plan, --permission-mode plan or defaultMode. Edit plans with Ctrl+G.
  • If you can describe the diff in one sentence, skip the plan.
  • Ask for a plan with a defined shape (steps, files, tests, risks), and save it to a file so it outlives the session.
