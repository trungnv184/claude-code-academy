Goals & Loops

By default the model decides when it's done, and the model is an optimist. This lesson is about moving the finish line out of the model's head and into something it can't argue with.

The optimist in the loop

Go back to the twelve lines of pseudocode in lesson 1. The loop ends when the model replies without asking for a tool. Nothing checks that the work is actually finished. The model simply stops wanting to do more.

That's fine for "rename this variable." It's a problem for "fix the checkout bug," because language models are trained to produce helpful-sounding completions, and few things sound more helpful than "Done! All tests pass." Sometimes that sentence is true. Sometimes the tests were never run. Sometimes three of them were quietly skipped. The model isn't lying in any meaningful sense. It reached a plausible stopping point and said a plausible thing.

An agent without a finish line stops when it feels done. An agent with a finish line stops when it is done.

We call this failure premature victory, and it's the most expensive failure mode in practice. A wrong approach is visible in the plan, and rule drift is visible in the diff. Premature victory looks exactly like success until you or your CI find out otherwise.

Finish lines the agent can't fake

The fix is to define "done" as something a machine checks, not something the model believes. Good finish lines share three properties:

  • External. The truth comes from a tool, not from the model's self-report: a test runner, a type checker, a linter, curl against a running server, a screenshot diff.
  • Binary or numeric. Exit code 0. Zero type errors. Lighthouse score ≥ 90. Coverage at least 80%. Not "clean," not "robust," not "works properly."
  • Visible. The evidence ends up somewhere the checker can see: the transcript, a log file, a CI status.
Fakeable finish lineUnfakeable version
"Fix the bug""Add a regression test that fails before the fix and passes after; npm test exits 0"
"Make it type-safe""tsc --noEmit reports 0 errors, and no new any or @ts-ignore appears in the diff"
"Make the page faster""Lighthouse performance ≥ 90 on /checkout in the CI run"
"Clean up the code""eslint . exits 0 with the stricter config in .eslintrc.strict.json"
"Migrate to the new API""grep -r legacyClient src/ returns nothing and the full suite passes"

Once you have a finish line like that, there are three escalating ways to enforce it. You can ask for it in the prompt, which is advisory and often enough. You can set a /goal, which a second model checks after every turn. Or you can write a Stop hook, a script that physically runs the tests before Claude may stop; that's covered in lesson 5. This lesson covers the middle option and the loops built on it.

How /goal actually works

/goal is the most direct way to give a session a finish line. You type a condition and Claude starts working on it immediately. After each turn, before Claude is allowed to stop, the condition is checked.

Under the hood, /goal is a prompt-based Stop hook scoped to your session. When Claude tries to end its turn, a small, fast model is asked whether the condition holds and answers one of three ways: met (Claude may stop), not yet met (Claude is sent back to work), or impossible (stop trying). You get the stop-gate behavior of lesson 5 without writing a script.

The one thing to understand: the evaluator can't run tools

The evaluator does not run your tests. It can't run anything. It reads what's already in the transcript and judges whether that text satisfies your condition. This has a direct consequence for how you write goals:

⚠
If it isn't in the transcript, it didn't happen

A condition like "the tests pass" invites Claude to say the tests pass. A condition like "npm test exits 0 and the output is shown in the transcript" makes Claude run the command where the evaluator can see the result. Always ask for visible evidence.

If you need a gate that executes a check itself, that's a command Stop hook (lesson 5). /goal trades that rigor for zero setup, and the trade is usually worth it as long as you ask for evidence.

The mechanics

CommandWhat it does
/goal <condition>Sets the goal and immediately starts a turn with the condition as the directive. Conditions can be long (up to 4,000 characters).
/goalShows the current goal's status.
/goal clearRemoves it. stop, off, reset, none and cancel work too. /clear also removes the goal.
  • One goal per session. Setting a new one replaces the old one. If you have three outcomes, combine them into one condition ("A and B and C").
  • It doesn't change your permission mode. In the default mode you'll still approve each edit and command, which defeats the point of an unattended run. Pair it with a mode that lets Claude act, such as auto mode, inside a project with sensible permissions.deny rules and hooks.
  • Always add a bound. End the condition with "or stop after 20 turns." That turns a potentially infinite loop into a bounded experiment.

It also works headless, which makes it a building block for scripts and CI:

# run a goal non-interactively; Ctrl+C interrupts it
claude -p "/goal CHANGELOG.md has an entry for every PR merged this week, or stop after 15 turns"

# watch progress as it happens
claude -p "/goal npm test exits 0 with output shown, or stop after 20 turns" \
  --output-format stream-json --verbose

Writing goals that converge

A good goal condition reads like an acceptance test. Here is the checklist the lab below uses, and the one I use every time:

  1. Name the evidence. Which command, which file, which output? "npm run typecheck exits 0" beats "no type errors."
  2. Make it measurable. Exit codes, counts, thresholds. Every subjective word ("clean," "properly," "better") is one the evaluator can't confirm. It will either accept it on faith or never accept it.
  3. Demand visibility. "…with the final output shown in the transcript."
  4. Bound it. "…or stop after N turns." Pick N at roughly two to three times what you'd expect.
  5. Scope it. "tests in tests/cart" converges faster than "all tests" in a repo with known-flaky e2e suites.
Goal conditionWhat happens
"make the cart work properly"Claude says "works properly now!" and the evaluator accepts it. False met.
"tests pass and the code is clean"Tests go green, but "clean" never becomes provable. Spins forever (or until the bound).
"npm test -- tests/cart exits 0 and npm run typecheck exits 0"Converges, but an impossible task (missing env var, flaky test) would never stop.
"…both exit 0, with the final output shown in the transcript, or stop after 15 turns"Converges on evidence, and gives up cleanly if it can't.

/loop: work on a timer

/goal answers "keep going until X." /loop answers a different question: "do this again every so often." It's a bundled skill that schedules a prompt to re-run inside your session.

# fixed interval (s, m, h, d; seconds round up to a minute)
/loop 5m check whether the deploy finished and summarize any errors

# no interval: Claude paces itself, between 1 minute and 1 hour
/loop keep an eye on the CI run for this branch and fix lint failures

# no prompt: runs .claude/loop.md (project) or ~/.claude/loop.md (user) if present,
# otherwise a built-in maintenance prompt
/loop

A few constraints worth knowing before you rely on it:

  • Your session has to be running. Loop tasks fire only while Claude Code is open and idle. Close the terminal and the loop stops. If you --resume or --continue, most interval tasks come back, but self-paced loops don't.
  • Recurring tasks expire after 7 days. This is a safety net against forgotten loops.
  • Stop a self-paced loop with Esc.
  • Commit .claude/loop.md if your team has a standard "babysit this repo" routine. Then a bare /loop does the right thing for everyone.
☁
Need it to run when your laptop is closed?

/schedule (alias /routines) creates cloud routines that run on a cron schedule without your machine, with a minimum interval of one hour. Use /loop for "while I'm working" and /schedule for "every morning at 8."

The Ralph loop: fresh context, persistent progress

There's an older, cruder and surprisingly effective pattern that predates /goal. Geoffrey Huntley popularized it as the "Ralph Wiggum" technique: run the agent in a plain shell while loop and feed it the same prompt every time. Each iteration starts with a fresh context window, so context rot never builds up. Continuity lives in files: a spec, a progress log and the git history.

ralph.shbash
#!/usr/bin/env bash
# Run Claude repeatedly on the same prompt until the work is done (or we hit a cap).
set -euo pipefail
MAX=25
for i in $(seq 1 "$MAX"); do
  echo "── iteration $i ──"
  claude -p "$(cat PROMPT.md)" \
    --permission-mode acceptEdits \
    --allowedTools "Read,Edit,Write,Bash(npm test *),Bash(git add *),Bash(git commit *)" \
    --max-turns 40
  # the exit condition is checked by the shell, not the model
  if grep -q "STATUS: COMPLETE" progress.md && npm test --silent; then
    echo "done after $i iterations"; exit 0
  fi
done
echo "hit iteration cap"; exit 1
PROMPT.mdmarkdown
# Task
Implement the features in SPEC.md, one at a time.

## Each iteration
1. Read progress.md to see what's done. Pick the next unchecked item.
2. Write a failing test for it, then make it pass.
3. Run `npm test`. Only if it exits 0: tick the item in progress.md and commit.
4. If every item is ticked and tests pass, write `STATUS: COMPLETE` at the top of progress.md.

Never mark an item done without a passing test. Keep commits small.

Notice where the finish line lives: in grep and npm test, run by the shell. The model can write "STATUS: COMPLETE" all it likes; the loop only exits if the tests agree. Notice also that the prompt never changes. All the state is in progress.md and git, which is exactly the "write state to files, not chat" advice from lesson 1 turned into an architecture.

🎼
When to use which

Use /goal for one task that fits comfortably in a session. Reach for a Ralph loop when the work is long enough that a single context window would rot: a 30-item spec, a big migration, an overnight run. Each iteration is a clean, cheap restart.

TDD is the original agent loop

Red, green, refactor is a loop with a built-in, unfakeable finish line, which is why test-driven development fits agents unusually well. The workflow that works:

  1. Ask Claude to write tests only, from the spec, and to confirm they fail. Tell it explicitly not to write the implementation yet.
  2. Commit the tests. Now they're a fixed target.
  3. Set the goal: "npm test exits 0 with output shown, without modifying anything under tests/, or stop after 20 turns."
  4. Review the diff. The tests did the arguing for you.

That "without modifying tests" clause matters. An agent under pressure to make tests pass will sometimes "fix" the test. Put the rule in the goal condition, and if it's important enough, enforce it with a hook that blocks edits to tests/ during implementation (lesson 5).

Runaway protection

Loops are where agents get expensive. A goal that never converges, or a Ralph loop with a bug in its exit condition, will happily burn turns until something stops it. Put a ceiling on every unattended run:

Key takeaways

  • Premature victory happens because the model decides when it's done. Move "done" into something external, binary and visible.
  • /goal is a session-scoped, prompt-based Stop hook: a fast model judges the transcript after each turn. Ask for evidence in the transcript, and always add "or stop after N turns."
  • Subjective words make goals either falsely met or never met. Write conditions like acceptance tests.
  • /loop repeats work while your session runs; /schedule runs routines in the cloud; a Ralph loop restarts fresh sessions with state in files.
  • Every unattended run gets a ceiling: turn bounds, --max-turns, --max-budget-usd, iteration caps.
