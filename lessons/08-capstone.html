Lesson 8 · Capstone project

Capstone: Ship a Real Project

Seven lessons, seven layers. Now we stack them. You'll build Snip — a small, real URL shortener — and by the end, your repo won't just contain an app. It'll contain the harness that built it, ready for the next feature and the next teammate.

60 min build9 milestonesTracker + replayQuiz

By the end of this capstone you will have

  • A working Express + SQLite URL shortener with a Vitest suite and a tiny HTML front end
  • A committed .claude/ folder: settings, three hooks, one skill, one reviewer agent
  • Shipped a feature with /goal, two more in parallel worktrees, and wired headless Claude into CI
  • A personal retro on what to keep, what to cut, and what to teach your team

The project, and the point

Snip is deliberately boring. Paste a long URL, get back http://localhost:3000/aZ3kq9, visit it, get redirected, and see a click count. Every developer has built something like it, which is exactly why it's a good capstone: you already know what "correct" looks like, so all of your attention can go to how the work gets done.

Here's the rule for the next hour: you don't write application code. You write context, plans, finish lines, guardrails, and helpers. Claude writes the code. When something goes wrong — and it will, a little — resist the urge to fix it by hand. Ask yourself which layer of the harness would have prevented it, and fix that.

An app is what you ship once. A harness is what ships every feature after it.

Track your progress as you go. The checklist below remembers where you left off, so you can split the capstone across sittings.

M1Hand-tune CLAUDE.md

Goal
A short, opinionated memory file that prevents the "amnesia" failure mode.
Layer
Context (lesson 2)
Time
10 minutes

/init describes what it sees. Your job is to add what it can't see: decisions, taste, and landmines. Replace the draft with something like this — note how little prose there is. Every line should change a behavior; if deleting a line wouldn't change what Claude does, delete it.

CLAUDE.md~40 lines
# Snip — URL shortener

## Commands
- `npm test` — Vitest, runs in <2s. Run it after every change.
- `npm run lint` — ESLint flat config. Must exit 0 before you say "done".
- `npm run dev` — server on http://localhost:3000

## Architecture
- `src/app.js` builds the Express app (no listen) → imported by tests via supertest
- `src/server.js` only calls `app.listen`
- `src/routes/*` → thin HTTP layer; `src/services/*` → logic; `src/db.js` → better-sqlite3
- `public/index.html` — single static page, vanilla JS, no framework

## Conventions
- ES modules, async/await, no classes unless state demands it
- Validate input at the route; services assume valid data
- Errors: `res.status(4xx).json({ error: "message" })` — never leak stack traces
- Short codes: 6 chars from nanoid's url-safe alphabet
- Every new route gets a test in `test/` named after the route file

## Never
- Never use an in-memory array as the store — always SQLite
- Never add a dependency without asking first
- Never edit `test/fixtures/*` to make a test pass

## Workflow
- For anything bigger than one file: plan first, write the plan to PLAN.md
- Spec lives in SPEC.md; the plan lives in PLAN.md — keep both current
- API reference: @docs/API.md
💡
Why "Never" lines live here and in hooks

CLAUDE.md is advisory — Claude will follow it most of the time. For anything where "most of the time" isn't good enough, M2 adds a hook. The CLAUDE.md line still helps: it stops Claude from trying, which saves a turn.

Checkpoint: git commit -m "docs: hand-tuned CLAUDE.md". Create an empty docs/API.md so the import resolves.

M2Settings, permissions & hooks

Goal
Fewer permission prompts for safe commands; hard blocks for dangerous ones; formatting and a test gate that run without anyone remembering.
Layer
Hooks (lesson 5)
Time
15 minutes

This is the milestone people skip, and the one that pays back most. Three hooks, one settings file:

HookEventJob
block-dangerous.shPreToolUse · BashExit 2 on rm -rf, force push, hard reset, DROP TABLE
format.shPostToolUse · Edit|WriteRun Prettier on the file that was just changed
stop-gate.shStopIf tests fail, refuse to stop and hand Claude the failure log
.claude/settings.jsoncommit this
{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Bash(npm test *)",
      "Bash(npm run lint)",
      "Bash(npx vitest *)",
      "Bash(git status)",
      "Bash(git diff *)",
      "Bash(git add *)",
      "Bash(git commit *)"
    ],
    "ask": ["Bash(npm install *)", "Bash(npm i *)"],
    "deny": ["Read(./.env)", "Bash(git push *)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-dangerous.sh" }]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/format.sh" }]
      }
    ],
    "Stop": [
      {
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/stop-gate.sh", "timeout": 120 }]
      }
    ]
  }
}
.claude/hooks/block-dangerous.shPreToolUse
#!/usr/bin/env bash
# PreToolUse(Bash): refuse destructive commands.
# Exit 2 = block the tool call; stderr is shown to Claude as the reason.
cmd=$(jq -r '.tool_input.command // ""')
if echo "$cmd" | grep -Eq 'rm -rf|git push .*(-f|--force)|git reset --hard|DROP TABLE'; then
  echo "Blocked by project policy: '$cmd'. If this is really needed, ask the user to run it." >&2
  exit 2
fi
exit 0
.claude/hooks/format.shPostToolUse
#!/usr/bin/env bash
# PostToolUse(Edit|Write): format the file Claude just touched. Never blocks.
file=$(jq -r '.tool_input.file_path // ""')
case "$file" in
  *.js|*.json|*.md|*.html|*.css) npx prettier --write "$file" >/dev/null 2>&1 ;;
esac
exit 0
.claude/hooks/stop-gate.shStop
#!/usr/bin/env bash
# Stop: Claude may only finish a turn while the test suite is green.
input=$(cat)
# If this stop was already caused by our block, don't loop forever — let it stop.
if [ "$(echo "$input" | jq -r '.stop_hook_active // false')" = "true" ]; then exit 0; fi
log=$(mktemp)
if ! npm test --silent >"$log" 2>&1; then
  echo "Tests are failing — fix them before finishing. Last 30 lines:" >&2
  tail -n 30 "$log" >&2
  exit 2
fi
exit 0
chmod +x .claude/hooks/*.sh

⚠️
The Stop gate is strong medicine

A test-gated Stop hook fires on every turn end — even when you just asked a question. On a tiny suite that's fine. On a slow one, gate it on whether source files actually changed (e.g. check git status --porcelain src test first), or rely on /goal for the finish line instead.

M3Spec by interview, then plan mode

Goal
A SPEC.md you agree with and a PLAN.md Claude will execute — before a single route exists.
Layer
Plan mode (lesson 3)
Time
10 minutes

Instead of writing a spec yourself, have Claude interview you. It is remarkably good at surfacing the questions you'd only discover halfway through implementation: what happens on duplicate URLs? Do codes expire? What's a valid URL?

Type
I want to build Snip, a URL shortener (see CLAUDE.md for stack). Interview me about it in detail — data model, validation, edge cases, error responses, what the front end needs. Ask one batch of questions at a time. Don't write code. When we're done, write the result to SPEC.md.

Answer honestly; say "you decide, keep it simple" where you don't care. Then clear the conversation — the spec is on disk, the interview chatter isn't needed — and switch to plan mode with Shift+Tab (twice, until the status bar reads plan mode on) or /plan:

Type
/clear
/plan Read SPEC.md and CLAUDE.md. Produce an implementation plan for the MVP: POST /api/links (create), GET /:code (redirect + count click), GET /api/links/:code (info), and public/index.html. Order the steps so each ends with a passing test. Include the SQLite schema.

Read the plan like a code reviewer. Push back on anything you'd push back on in a PR — "use a UNIQUE index rather than checking in code", "return 422 not 400 for bad URLs". When it's right, approve it and ask Claude to save it:

Save this plan to PLAN.md as a checklist, then stop.
Checkpoint: SPEC.md and PLAN.md committed. No src/ files yet. You've spent ~15 minutes and written zero code — and you've already caught the decisions that cause rewrites.

M4Implement with /goal

Goal
The MVP, built autonomously, with a finish line Claude can't fake.
Layer
Goals & loops (lesson 4)
Time
10 minutes of yours, ~15 of Claude's

Switch to auto-accept edits (Shift+Tab until accept edits on) so you aren't approving every file. Your hooks are the safety net now. Then set the goal:

Type
/goal Implement PLAN.md. Done means: all vitest tests pass, npm run lint exits 0, and POST /api/links + GET /:code work per PLAN.md (show the test output proving it), with PLAN.md checkboxes ticked — or stop after 25 turns.

Setting a goal immediately starts working on it. After every turn, a small, fast evaluator model reads the transcript and decides met, not yet met or impossible. Two details matter here:

  • The evaluator can't run tools. It judges what Claude has shown. That's why the condition says "show the test output proving it" — you're asking Claude to put evidence in the transcript.
  • "Or stop after 25 turns" is your budget. Without a stop clause, a goal that's impossible as written can burn a lot of turns before the evaluator calls it.

Meanwhile your Stop hook is quietly doing its job: any time Claude tries to end a turn with red tests, it gets the failure log back instead. The goal sets the destination; the hook guarantees the floor.

Checkpoint: the evaluator reports the goal met. Now you verify — npm run dev, shorten a link in the browser, click it. Read the diff. Commit at green: feat: snip MVP.

M5Teach it once: a custom skill

Goal
Package "how we add an endpoint here" so every future endpoint follows the same recipe.
Layer
Skills (lesson 6)
Time
10 minutes

You'll add more endpoints to Snip. Each time, you want the same shape: failing test first, thin route, logic in a service, validation, docs updated. That's a recipe — and recipes belong in skills, not in your head or in a 300-line CLAUDE.md.

.claude/skills/add-endpoint/SKILL.mdloaded only when relevant
---
name: add-endpoint
description: Add a new HTTP endpoint to Snip (Express route + service + Vitest test + API docs). Use when the user asks for a new API route, endpoint, handler, or stats/analytics URL.
argument-hint: "[METHOD /path] [what it should return]"
allowed-tools: Read, Grep, Edit, Write, Bash(npm test *), Bash(npm run lint)
---

# Add an endpoint to Snip

Target: $ARGUMENTS

1. **Test first.** Create or extend `test/<route-file>.test.js` using supertest
   against `src/app.js`. Cover: happy path, 404 for unknown code, 4xx for bad input.
   Run `npm test` and confirm the new test FAILS for the right reason.
2. **Service.** Put logic in `src/services/<name>.js`. Pure functions taking `db`.
   Use prepared statements — never string-concatenate SQL.
3. **Route.** Add a thin handler in `src/routes/`, register it in `src/app.js`.
   Validate params at the route. Errors: `res.status(4xx).json({ error })`.
4. **Verify.** `npm test` and `npm run lint` must both pass.
5. **Document.** Append the endpoint to `docs/API.md` using the format in
   `api-entry-template.md` (next to this file).
6. Report: the route, the test names, and the passing test output.
.claude/skills/add-endpoint/api-entry-template.mdsupporting file
### `METHOD /path`
One-sentence purpose.

**Response 200**
```json
{ "example": "body" }
```
**Errors:** `404` unknown code · `422` invalid input

Note that the request below never mentions the skill. The description is what Claude matches against — which is why it's written as "Use when the user asks for…".

Type
Add an analytics endpoint: GET /api/links/:code/stats returning total clicks, clicks per day for the last 7 days, and the created_at date.
Checkpoint: you see Claude load the add-endpoint skill, write a failing test first, then implement. docs/API.md gains an entry in the template's format. If the skill didn't trigger, sharpen its description — that's the lesson 6 debugging loop.

M6Sub-agents & parallel worktrees

Goal
An independent reviewer for every diff, and two features built at the same time without stepping on each other.
Layer
Sub-agents (lesson 7)
Time
15 minutes

A reviewer with fresh eyes

The agent that wrote the code is the worst-placed agent to review it: its context is full of its own reasoning. A sub-agent starts clean, sees only the diff, and is restricted to read-only tools so it can't "helpfully" fix things mid-review.

.claude/agents/code-reviewer.mdsub-agent
---
name: code-reviewer
description: Reviews uncommitted changes in Snip for bugs, security issues, and missing tests. Use proactively after implementing a feature and before committing.
tools: Read, Grep, Glob, Bash
model: sonnet
color: purple
---

You are a senior reviewer for Snip, a small Express + SQLite URL shortener.

Review ONLY the current changes (`git diff` and `git diff --staged`).
Do not edit files. Your output is a review, not a fix.

Check, in priority order:
1. Correctness: off-by-one, wrong status codes, unhandled null/undefined
2. Security: SQL built by string concatenation, open redirects (we must only
   redirect to http/https URLs), unvalidated input, leaked stack traces
3. Tests: every new branch has a test; tests assert behavior, not implementation
4. Conventions from CLAUDE.md

Output format:
- **Blocking** — must fix, with file:line and a one-line suggested fix
- **Should fix** — worth doing in this PR
- **Nit** — optional
End with a one-line verdict: APPROVE or CHANGES REQUESTED.
Type
Use the code-reviewer agent to review the stats endpoint changes. Then fix every Blocking item and re-run the reviewer until it approves.

Two features, two worktrees, zero collisions

Next up: custom aliases (/my-talk instead of /aZ3kq9) and link expiry. They're independent, so build them simultaneously. Each --worktree session gets its own checkout and branch, so two agents can edit src/ at the same time without overwriting each other.

# terminal 1
claude --worktree aliases
# terminal 2
claude --worktree expiry
Terminal 1
/goal Add custom aliases per SPEC.md: POST /api/links accepts optional "alias" (3–32 chars, [a-z0-9-]), 409 if taken. Use the add-endpoint conventions. Done when tests + lint pass and the code-reviewer agent approves — or stop after 20 turns.
Terminal 2
/goal Add link expiry: optional "expiresInDays" on create; GET /:code returns 410 Gone after expiry. Done when tests + lint pass and the code-reviewer agent approves — or stop after 20 turns.

While they run, you're free. That's the orchestrator stage from lesson 1: you decomposed the work, set verifiable finish lines, and now you review results instead of keystrokes. When both finish, merge — each worktree session works on its own branch (by default worktree-aliases and worktree-expiry):

git merge worktree-aliases
git merge worktree-expiry   # both touch the create route; resolve with Claude if needed
npm test
Checkpoint: both features merged, suite green, reviewer approved each branch. If the second merge conflicted, ask Claude to resolve it and run the tests — conflict resolution is just another act → verify loop.

M7/loop & headless Claude in CI

Goal
Agents that keep working when you're not typing: one babysitting your PR, one reviewing every PR in CI.
Layer
Loops (lesson 4) + automation
Time
10 minutes

Babysit the PR with /loop

Push a branch and open a PR (you push — remember, your settings deny git push for Claude). Then:

Type
/loop 10m Check the CI status of my open PR with `gh pr checks`. If a check failed, read its log with `gh run view --log-failed`, fix the cause locally, run tests, and commit. Tell me when a push is needed. When all checks are green, say so and stop.

/loop re-runs the prompt every 10 minutes while the session is open and idle. Leave out the interval and Claude paces itself. Press Esc to stop a self-paced loop. Notice the division of labor: the loop does the watching and fixing; the irreversible action — pushing — stays with you.

Headless review on every PR

claude -p runs a single prompt non-interactively — perfect for CI. The official GitHub Action wraps it. The quickest setup is /install-github-app from inside Claude Code; here's the manual version with a custom review prompt:

.github/workflows/claude-review.ymlCI
name: Claude PR review
on:
  pull_request:
    types: [opened, synchronize]
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 0
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Review this PR against CLAUDE.md conventions. Focus on correctness,
            open-redirect risks, and missing tests. Post one concise review comment.
          claude_args: "--max-turns 10"

And because the harness lives in the repo, the CI agent reads the same CLAUDE.md, the same skills, the same agents. Locally or in CI, it's one team, one set of rules. For quick scripts, the bare CLI works too:

claude -p "Summarize what changed on this branch vs main for a release note" \
  --output-format json --max-turns 5 | jq -r '.result'
Checkpoint: a PR shows a review comment from Claude. The loop told you when CI went green.

The compounding loop

Each retro makes the next project faster: a CLAUDE.md line here, a sharper hook there, a new skill. Six months in, your .claude/ folder is the most valuable thing in the repo — it's how your team thinks, made executable.

Key takeaways

  • Harness before code. Memory, guardrails and a plan took the first 40 minutes — and made the next 20 almost boring.
  • Each layer has one job. CLAUDE.md informs, plans align, goals define done, hooks enforce, skills repeat, sub-agents isolate.
  • Evidence beats assertions. Goal conditions ask for shown proof; Stop hooks check it for real; a reviewer agent checks it with fresh eyes.
  • Commit the harness. It's the part of the project that makes every future feature cheaper — for you and everyone who clones the repo.
