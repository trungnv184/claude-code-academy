Sub-agents & the Orchestra

One agent with a perfect harness still has one context window and one pair of hands. Sub-agents give you more of both, but every extra agent also costs coordination. This lesson covers when the orchestra plays in tune, and when it's just noise.

  • Explain the four reasons to delegate: context isolation, specialization, parallelism and tool restriction
  • Write sub-agent definitions in .claude/agents/ and invoke them automatically, explicitly or by @-mention
  • Apply four proven patterns: fan-out research, writer/reviewer, test runner and parallel worktrees
  • Predict when adding agents won't help, using a dependency graph rather than optimism

Why one agent isn't enough

Go back to the loop from lesson 1. Everything the agent touches (every file read, grep result and 2,000-line test log) lands in a single context window and stays there. For a 20-minute task, that's fine. For a feature that spans the API, the database, the UI and the docs, the window ends up holding four tasks' worth of debris, and the agent working on the docs is still paying attention to a stack trace from the migration.

A sub-agent is the fix. It's a separate Claude instance with its own context window, its own system prompt, and optionally its own tools and model. The main agent hands it a brief. It works, possibly reading dozens of files. Then it hands back a summary. Only the summary enters the main context.

The main reason to use a sub-agent is to keep your main context clean. Speed is a secondary benefit.

There are four distinct reasons to delegate, and it helps to know which one you're after:

ReasonWhat you getTypical agent
Context isolationNoisy exploration stays out of the main window; you get a 10-line answer, not 40 filesExplore, researcher
SpecializationA focused system prompt beats a general one; "you are a security auditor" changes what gets noticedsecurity-auditor, code-reviewer
ParallelismIndependent tasks run at the same time; wall-clock dropsSeveral general-purpose agents
Tool restrictionA reviewer that can't edit can't "fix" things silently; least privilege for agentsRead-only reviewer

Built-in agents you already have

You've been using sub-agents since lesson 1, maybe without noticing. Claude Code ships with several built-ins and delegates to them on its own:

AgentToolsUsed for
ExploreRead-onlyFast codebase search and mapping: "where is X handled?"
PlanRead-onlyResearch during plan mode, so planning doesn't bloat your context
general-purposeAll toolsMulti-step tasks that need to both read and act

When the transcript shows a line like Explore(…) or Task(…), that's delegation in progress. You don't need any configuration to benefit from it, but you can ask for it explicitly: "use an Explore agent to find every place we parse dates."

Defining your own agents

Custom agents are markdown files with YAML frontmatter. The body is the agent's system prompt. As with skills, location decides scope:

  • .claude/agents/*.md: project agents, shared with the team through git
  • ~/.claude/agents/*.md: your personal agents, available in every repo
  • Plugin agents/ directories, plus a --agents CLI flag that takes JSON for one-off sessions

The fastest way to create one is /agents, which opens an interactive manager that can generate a first draft for you to edit. Claude watches the agents directories, so most edits take effect without a restart. Identity comes from the name field, not the filename.

Three ways to invoke

  1. Automatic. Claude reads every agent's description and delegates when a task fits. Phrases like "Use proactively after code changes" in the description make this more likely.
  2. Natural language. "Use the code-reviewer agent to review my staged changes." This is explicit and predictable.
  3. @-mention. Type @ and choose the agent, e.g. @"code-reviewer (agent)". You can also run a whole session as an agent with claude --agent code-reviewer.

Nesting, concurrency and backgrounding

Sub-agents can spawn their own sub-agents, up to a default depth limit of a few layers below the main conversation. You can turn nesting off with CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1. Many sub-agents can run concurrently. Press Ctrl+B to send a running task to the background and keep talking to the main agent while it works.

⚠
Depth is not a feature to max out

Every level of nesting is another hop where a brief can lose detail. Most real workflows need one level: a lead and its specialists. If you find yourself designing a three-level hierarchy, you probably want a written plan and several sessions instead.

Four patterns that earn their keep

1. The fan-out researcher

Before a cross-cutting change, send several Explore agents out in parallel, each with a narrow question: "how does auth issue tokens?", "where are sessions persisted?", "which UI components read the user?". Each one reads freely in its own window and returns a page. The lead then plans with three clean summaries instead of 90 raw files. This is the cheapest, safest parallelism there is, because nothing is being edited.

2. Writer / reviewer: fresh eyes

An agent reviewing its own code has the same blind spots it had while writing it. It remembers what it meant, so it reads intent where there's a bug. A reviewer sub-agent starts with a clean context and sees only the diff and the codebase. Give it read-only tools so that it reports rather than "fixes", and have the author address the findings. This is the single highest-value multi-agent pattern, and it costs one extra agent.

3. The test runner

Test output is the noisiest thing an agent reads. A dedicated test-runner agent runs the suite, reads the 4,000-line log, and returns "3 failures, here are the assertions and the likely cause." The main context gets the diagnosis without the log.

4. Parallel sessions in worktrees

When the tasks really are independent (two features, or a bug fix next to a refactor), you can run separate Claude sessions in separate git worktrees. Each gets its own checkout and branch, so the sessions can't trample each other's files:

# each command opens a session in .claude/worktrees/<name> on branch worktree-<name>
claude --worktree feature-sessions
claude --worktree fix-coupon-tax     # in another terminal

For sub-agents, isolation: worktree in the frontmatter gives you the same guarantee automatically. Either way, the merge is still yours. Parallel work moves the hard part to integration; it doesn't remove it.

Conductor vs. orchestrator

Addy Osmani's essay "The Code Agent Orchestra" gives the clearest framing I know for how the engineer's job changes here. Paraphrasing: as a conductor, you work with one agent in real time, guiding it turn by turn and keeping the whole piece in your head. As an orchestrator, you step back. You break work into well-specified parts, hand them to several agents running at once, and spend your time on specs, review and integration instead of on individual keystrokes.

The shift sounds like a promotion, and in a way it is, but it changes what you're good for. The orchestrator's leverage comes almost entirely from two skills: decomposition (cutting work along seams where agents won't collide) and verification (knowing quickly whether what came back is right). Without both, more agents just produce more plausible-looking diffs to untangle. Read the full essay; it's the natural next step after this lesson.

When not to use more agents

Multi-agent setups are fashionable, so the counter-arguments deserve the same weight. The lab shows each of them in numbers:

  • Dependencies cap your speed-up. If only three tasks can ever be ready at once, the fourth and fifth agents sit idle. Draw the dependency graph before you pick a team size.
  • Every agent pays to load context. A fresh sub-agent has to re-read the files it needs. Five agents that each read the same module cost five times as much. Parallelism trades tokens for wall-clock time; that trade is only worth making when time is the bottleneck.
  • Shared files mean merge conflicts. Two agents editing session.ts at the same time will produce a conflict or, worse, a clean merge that is semantically wrong. Assign file ownership, sequence the overlap, or isolate with worktrees.
  • Tightly coupled work doesn't split. A refactor where every change depends on the last one is a single train of thought. Splitting it gives you several agents that each understand a third of the design.
  • Briefs lose information. A sub-agent knows only what its brief says plus what it reads. Constraints you mentioned to the lead 40 turns ago don't arrive unless you put them in the brief, in CLAUDE.md, or in a file.
💡
A good default

Start with one main agent, Explore for research, and a read-only reviewer at the end. Add parallel implementers only when you have a written plan with clear file ownership and the dependency graph actually allows it.

Three agents worth stealing

1. A read-only code reviewer

.claude/agents/code-reviewer.mdmarkdown
---
name: code-reviewer
description: Reviews a diff for bugs, missed edge cases and convention violations. Use proactively after implementing a feature or before committing.
tools: Read, Grep, Glob, Bash(git diff *), Bash(git log *)
model: sonnet
color: orange
---

You are a senior reviewer seeing this change for the first time.

1. Run `git diff` (or `git diff --staged` if asked) to get the change.
2. For every changed function, read its callers. Bugs live at boundaries.
3. Check: error handling, null/empty inputs, off-by-one, concurrency,
   security (injection, authz), and the conventions in CLAUDE.md.
4. Do NOT edit files. You report; the author fixes.

Output, most severe first:
- **file:line** — the problem, a concrete failing input, and the suggested fix.
End with a one-line verdict: SHIP, SHIP WITH FIXES, or BLOCK.
If you find nothing, say so plainly. Don't pad the list.

2. A test runner that swallows the noise

.claude/agents/test-runner.mdmarkdown
---
name: test-runner
description: Runs the test suite and type checker and reports only the failures with likely causes. Use after code changes or when asked to run tests.
tools: Read, Grep, Glob, Bash(pnpm test *), Bash(pnpm typecheck)
model: haiku
maxTurns: 15
---

Run `pnpm test` and `pnpm typecheck`.

If everything passes, reply with a single line: "✓ N tests passed, 0 type errors."

If anything fails, for each failure report:
- test name and file:line
- the assertion (expected vs received), max 5 lines
- the most likely cause, after reading the code under test

Never paste full logs. Never modify source or test files.

3. A security auditor

.claude/agents/security-auditor.mdmarkdown
---
name: security-auditor
description: Audits code for security vulnerabilities — injection, auth/authz gaps, secrets, unsafe deserialization, SSRF. Use when changes touch auth, user input, file paths, external requests or secrets.
tools: Read, Grep, Glob
model: opus
permissionMode: plan
---

You are an application security engineer. Assume every input is hostile.

Check the changed code (and what it calls) for:
- Injection: SQL, shell, path traversal, template, prototype pollution
- AuthN/AuthZ: missing checks, IDOR, trusting client-supplied IDs or roles
- Secrets: hardcoded keys, tokens in logs, .env contents leaking into output
- External requests: SSRF, unvalidated redirects, missing timeouts
- Data exposure: over-broad API responses, verbose error messages

For each finding: severity (critical/high/medium/low), file:line, a concrete
exploit scenario, and the fix. No theoretical findings without a code path.

Key takeaways

  • A sub-agent is a separate context window with its own prompt, tools and model. Its main value is keeping the main context clean.
  • Delegate for one of four reasons: isolation, specialization, parallelism or tool restriction. Know which one you want.
  • Define agents in .claude/agents/*.md with a sharp description. Restrict tools to the minimum the role needs.
  • The highest-value pattern is the fresh-context reviewer. Fan-out research is the safest form of parallelism.
  • More agents give diminishing returns. Dependencies, context-loading cost, shared files and coupling all argue for fewer.
